# SmartDNS и старые ASUS

SmartDNS — необязательный DNS-компонент. Он помогает воспроизвести условия,
в которых проверялась стратегия: выбранные DNS-серверы, DoT/DoH, правила для
отдельных доменов и явно заданные ответы. Сам SmartDNS не заменяет NFQWS2
и не гарантирует доступность сервиса.

Два резолвера могут вернуть разные адреса одного сервиса. От адреса зависят
доступность CDN, маршрут и поведение фильтрации. Поэтому результат стратегии
нужно оценивать вместе с её DNS-настройками. Это не означает, что каждой
стратегии необходим SmartDNS: иногда достаточно штатного DNS ASUS.

## Версия SmartDNS и совместимость с DNS-сервисом

Одна команда `opkg install smartdns` может дать разные версии. В проверенных
17 октября 2026 репозиториях Entware для `armv7-2.6` предлагается
`1.2023.43-1`, для `armv7-3.2` и `aarch64-3.10` — `46.1-1`.
Последний проверенный релиз самого SmartDNS —
[48.4](https://github.com/pymumu/smartdns/releases/tag/Release48.4).
Совместимость конкретного DNS-профиля проверяется отдельно от номера версии.

На самом 87U выполнен ограниченный опыт с отдельным процессом на loopback-порту.
В каждой фазе проверены три имени: example.com, www.youtube.com и image.tmdb.org.
Один upstream задан по IP, без запасного DNS; для TLS указаны CA, SNI и имя
сертификата. Между двумя правильными проверками имя сертификата намеренно
заменялось неправильным. Рабочий SmartDNS и путь DNS клиентов не менялись.

| Клиент и upstream | Правильное имя → неправильное → правильное |
|---|---|
| Entware SmartDNS 43, Quad9 DoT | 3/3 → 0/3 → 3/3 |
| Entware SmartDNS 43, Cloudflare DoH | 3/3 → 0/3 → 3/3 |
| Entware SmartDNS 43, Quad9 DoH | 0/3 → 0/3 → 0/3; при правильном имени сервер возвращает HTTP 505 |
| Upstream SmartDNS 48.4, тот же Quad9 DoH | 3/3 → 0/3 → 3/3 |

В отрицательных фазах журналы подтверждают отказ проверки сертификата.
Quad9 прекратил поддержку HTTP/1.1 в DoH с 15 декабря 2025 года:
[объяснение провайдера](https://docs.quad9.net/FAQs/#dns-over-https-no-http11-support).
На 87U обычный curl по HTTP/1.1 получил тот же 505. Поэтому надписи «есть DoH»
недостаточно: важны версия клиента, поддержка HTTP/2 и выбранный upstream.
Результат не означает, что весь DoH в версии 43 не работает: Cloudflare
в том же опыте прошёл проверку. Версия 46.1 этим опытом не испытывалась.

Для инструкции это означает: указывать версию и DNS-профиль вместе.
Проверенный профиль 48.4 нельзя автоматически объявлять проверенным для 43
или 46.1. Для Quad9 DoT на 43 получен отдельный положительный результат;
для Quad9 DoH на 87U подтверждён вариант 48.4. Полная установка пакета,
поведение после boot и работа клиентских приложений — отдельные проверки.
Этот опыт использовал извлечённый бинарник Entware 43, а не новую установку
через opkg. Ранее установленная 48.4 сохранена с исходными PID и конфигами.

У upstream 48.4 бинарник также зависит от комплектного загрузчика и библиотек;
отдельная копия ELF без нужного каталога запуска не исполнилась. Используйте
пакет и его launcher, а не случайную замену одного исполняемого файла.

## Общий пример для старых семейств

Короткая последовательность первого запуска — в [кратком гайде](QUICKSTART.md).
Официальные материалы: [установка для Entware](https://pymumu.github.io/smartdns/en/install/entware/)
и [настройка SmartDNS](https://pymumu.github.io/smartdns/en/config/basic-config/).
Установочный пример upstream использует старые `ipkg` и `mipsbig`, а один
из вариантов меняет режим dnsmasq. Его команды нельзя буквально переносить
на испытанный ARMv7 ASUS с существующей Entware. Ниже описана наша схема
с сохранением dnsmasq; полный пользовательский онлайн-путь установки 48.4
ещё проходит подготовку. Ссылку на него нужно добавлять в README и WebUI
вместе с готовой проверенной инструкцией, а не подменять её общим скачиванием.

### Что понадобится владельцу

- Подходящая стабильная прошивка для своей модели и рабочая Entware. Для
  испытанного 87U это Merlin 384.13_10 и armv7-2.6.
- Подготовленный USB-накопитель с местом для Entware, зависимостей и обновления.
  Объём пакета и свободная RAM проверяются отдельно: USB не добавляет ОЗУ.
- Совместимый обработчик NFQUEUE. Для точного 87U/384.13_10 пакет содержит
  проверенный дополнительный профиль и сам проверяет его перед загрузкой.
  У других моделей обработчик может уже входить в прошивку.
- Выбранный клиент для обработки и понятные DNS-условия стратегии. В проверке
  хватило одного DoT; отдельным сервисам понадобился подходящий адрес CDN.
- Проверка фактического поступления пакетов и полных ответов нужных сервисов.
  Объём RAM испытанного роутера — 256 МиБ; расход и границы замера приведены ниже.

Пакет сам выбирает подходящие утилиты и проверяет направление conntrack.
Владельцу проверенного профиля не требуется повторять сборку модуля или наш
испытательный полигон. Виртуальный LAN-клиент использован для контролируемого
сравнения; это не зависимость установки. Если профиль ещё не проверен,
диагностика модели, прошивки, очереди и DNS помогает подготовить следующий
совместимый вариант. Успех 87U — пример этого пути, а не гарантия для каждого
старого ASUS.

### Какие особенности уже учтены в пакете

На старом ASUS важно совпадение прошивки, ядра и Entware. Простого запуска
процесса недостаточно. Для проверенного профиля следующие действия выполняет
сам пакет; вручную подменять системные утилиты владельцу не требуется.

| Выявленная особенность | Как она учтена и что проверять владельцу |
|---|---|
| Правило NFQUEUE добавляется, но обработчика очереди в ядре нет | Точный профиль RT-AC87U/384.13_10 проверяет штатные файлы и подключает совместимый дополнительный модуль. На другой прошивке этот модуль автоматически не применяется |
| Штатные и Entware iptables ведут себя по-разному | Выбирается совместимая пара iptables/restore, а направление conntrack проверяется реальным локальным пакетом. Не заменяйте системные файлы и не копируйте настройки направления между моделями |
| Сжатый движок работает, но старое ядро мешает подтвердить его PID | Для legacy используется распакованный вариант того же закреплённого движка. Проверки принадлежности процесса сохраняются |
| Системная утилита NVRAM находится по другому пути | WebUI выбирает доступный штатный путь из фиксированного списка. Это исправляет чтение статуса и само по себе не меняет настройки |
| Процесс, привязка очереди и обработка трафика — разные состояния | Смотрите все три показателя, затем проверяйте нужный сервис. Номер очереди 300 сам по себе не подтверждает приём пакетов |
| USB и DNS готовы не сразу после загрузки | Для проверенной связки SmartDNS ожидание процесса и DNS-сокетов предшествует перенаправлению dnsmasq. Отдельно проверяются загрузка с USB и свежий DNS-запрос |

Для другой версии прошивки может понадобиться отдельный профиль и проверка.
Успех загрузки модуля не означает, что его можно переносить на похожий роутер.
Изменение ядра или перепрошивка в подтверждённом опыте не потребовались.

### Как читать статусы панели

| Показатель | Понятный смысл |
|---|---|
| «ARK не загружен» | Для пути NFQUEUE это благоприятное состояние. Оно не подтверждает остальные условия работы стратегии |
| Внутренний флаг IDS — «Неизвестно» | Прошивка не предоставила значение либо его не удалось прочитать. Это не доказательство включённого IDS или неисправности; пояснение открывается знаком вопроса |
| «Процесс NFQWS2 запущен» | Движок существует; поступление пакетов нужно проверить отдельно |
| Очередь 300 с зелёной галочкой, «Привязана» | Userspace-обработчик подключён к этой очереди. Такой же смысл у другого корректного номера очереди |
| Счётчик растёт во время контрольной проверки | Пакеты попали в очередь. Доступность сайта, полная загрузка и работа приложения проверяются отдельно |

Нулевой счётчик сразу после запуска возможен. Откройте нужный сервис
именно с выбранного для обработки устройства и выполните проверку поступления
пакетов. Если источником является сам роутер, см. пояснение ниже: его запросы
не равнозначны запросам телефона за LAN.

Основной пользовательский вариант — **Entware на внешнем USB-накопителе**.
На испытательном 87U использована уже подготовленная ext4-флешка: имеющиеся
каталоги сохранены, тестовая установка находится в отдельном каталоге.
Форматировать занятый накопитель ради повторения примера не требуется.

Сначала определите платформу, не устанавливая пакеты вслепую:

```sh
uname -rm
readlink /opt
cat /proc/mounts
df -k /tmp /jffs /opt
/opt/bin/opkg print-architecture
```

Последняя команда доступна после установки Entware. Если `/opt` ещё не
смонтирован, это отдельный этап подготовки накопителя. Не заменяйте существующую
Entware и не ставьте второй набор поверх неё.

| Семейство | Примеры и ориентир для Entware | Граница этого испытания |
|---|---|---|
| Старые ARMv7, Linux 2.6.36 | RT-AC56U, AC68U, AC87U, AC3200, AC88U, AC3100, AC5300; `armv7sf-k2.6` | SmartDNS 48.4 и USB-путь проверены на AC87U; NFQUEUE проверяется отдельно на каждой прошивке |
| ARMv7 с Linux 3.2 и новее | Например RT-AC58U; `armv7sf-k3.2` | Другая ветка ABI и возможны другие механизмы автозапуска |
| AArch64 с Linux 4.1 и новее | Например RT-AC86U; обычно `aarch64-k3.10` | Выбор подтверждается установленным Entware, а не только процессором |
| Старые MIPSel, Linux 2.6.22 | RT-N16, RT-N66U, RT-AC66U без B1; отдельный Entware-backports / legacy feed | Нынешний пакет NFQWS2 проекта MIPS не поддерживает; SmartDNS требует отдельного нативного испытания |

Эти ориентиры описаны в [документации Entware](https://github.com/Entware/Entware/wiki/Install-on-Asus-stock-firmware).
RT-AC66U и RT-AC66U B1 — разные платформы. MIPS и MIPSel также не взаимозаменяемы.
Наличие подходящего имени файла в upstream не подтверждает работу на старом ядре.

Для Merlin используйте [профильную инструкцию Entware](https://github.com/Entware/Entware/wiki/Install-on-Asuswrt-Merlin-firmware).
Hooks Merlin нельзя автоматически переносить на штатную ASUSWRT: способы
автозапуска отличаются и зависят от версии прошивки.

Одинаковый порядок проверки для каждого семейства:

1. Сохранить рабочие DNS-настройки и hooks, определить накопитель и ABI.
2. Установить подходящий SmartDNS и проверить реальную версию и файлы.
3. Запустить его на localhost:6053, проверить upstream и сертификаты отдельно
   от перенаправления клиентов.
4. Подключить штатный dnsmasq к SmartDNS и проверить внешние и локальные имена.
5. Проверить resolver самого роутера и адрес DNS, который получают клиенты.
6. Проверить автозапуск после полной перезагрузки с USB, снова выполнить запросы.
7. Проверить отключение схемы и возврат к прежнему DNS. Только после этого
   считать инструкцию воспроизводимой на данной модели и прошивке.

Это общий шаблон испытания. Подтверждённые модели добавляются по результатам,
а не по сходству названия или номеру ядра.

## Что проверено на RT-AC87U

Аппаратная проверка выполнена на Asuswrt-Merlin **384.13_10**, Linux
**2.6.36.4brcmarm**, ARMv7 и Entware **armv7-2.6**. Это результат для одной
конкретной прошивки, а не обещание поддержки всего семейства.

| Компонент | Результат |
|---|---|
| SmartDNS Release 48.4, официальный ARM optware runtime | Нативный запуск, ответы DNS, проверка сертификатов DoT/DoH |
| Копия профиля с 8 DoT и 7 DoH | Все 15 upstream ответили при раздельных проверках; отдельные домены проверены также через общий профиль |
| Штатный dnsmasq перед SmartDNS | Ответы внешних имён и локального имени роутера сохранены; dnsmasq и DHCP не заменяются |
| Entware на USB ext4 | Копия сверена по содержимому, ссылкам и правам 1383 элементов; после перезагрузки восстановились монтирование, SmartDNS, dnsmasq и resolver роутера |
| Внутренний JFFS | Лабораторный резерв сохранён; его запуск проверен отдельно |
| WebUI NFQWS2 | Нативный сервер вернул страницу HTTP 200; PHP 8.2.8 выполнил проверку входа и вернул 401 без авторизации |
| Движок NFQWS2 / NFQUEUE | В штатном образе нет backend очереди; с отдельно собранным модулем подтверждены приём пакетов, возврат трафика и контрольный TCP-обход |

Наличие `xt_NFQUEUE.ko` и успешное добавление правила NFQUEUE ещё не доказывают,
что ядро передаёт пакеты userspace-процессу. В исходном состоянии штатный
iptables принимал правило, но движок не мог зарегистрироваться в обработчике.
Последующий опыт с отдельным `nfnetlink_queue.ko` из исходников точной
Merlin 384.13_10 устранил эту причину: модуль загрузился без перепрошивки,
NFQWS2 подключился от UID/GID 65534, счётчик очереди вырос на реальном запросе.
Проверены также выгрузка и повторная загрузка модуля. Это отдельная
лабораторная проверка. В новой ARMv7-сборке есть узкий профиль дополнительного
модуля только для точного RT-AC87U/384.13_10: модель, версия, архитектура и хэши
штатных файлов должны совпасть. Он подключается при запуске службы, без force
и без изменения образа прошивки. Это не универсальный модуль для старых ASUS.
Кроме того, штатный iptables и iptables из Entware по-разному принимали
conntrack match. Не следует ослаблять проверки установщика ради зелёного статуса.

Контроль HTTPS выполнен на одном фиксированном адресе и с неизменным
вышестоящим маршрутом. Без обработки успешных загрузок не было в пяти
попытках до и пяти после; с TLS-фейком и `multidisorder` получены пять полных
HTTP 200, по 96 400 байт, с проверкой сертификата и окончанием HTML.
Один `multidisorder` проходил TLS, но большая страница зависала после
18–20 КБ. Поэтому одного успешного HEAD или появления HTTP 200 недостаточно.
Accept-only очередь отдельно пропустила две полные загрузки примерно по
960 КБ. Это не проверка скорости, видео, QUIC/UDP, LAN-клиентов или всех сайтов.
Через установленный пакет также проверены запуск, остановка и include одного
контрольного источника: 0/3 полных ответов до, 5/5 с обработкой и 0/3 после.
Пакет определяет совместимую пару iptables/restore и фактическую семантику
conntrack, использует частный ip и распакованный движок. Локальная проверка
не заменяет испытание отдельного устройства за LAN-портом.

### Один DoT и самостоятельная обработка старого роутера

Следующая проверка использовала **один Quad9 DoT**, без запасных DNS:
`dnsmasq :53 → SmartDNS :6053 → 9.9.9.9:853`. Имя сертификата —
`dns.quad9.net`, проверка по CA включена. Кеш отключён для опыта.
Это показывает, что для проверенных результатов не требуются 15 резолверов.

Пакеты отдельного виртуального Linux-клиента поступали в мост LAN самого
87U, затем проходили его forwarding, NAT и очередь NFQUEUE. Сетевые интерфейсы
и маршруты ПК не менялись. NFQWS2 вышестоящего роутера на время сравнения
выключен, а тестовый источник не входит в обработку основного ASUS. Адреса
получены через этот единственный DoT и зафиксированы между фазами.

| Проверка полного HTTPS-ответа | NFQWS2 87U выключен, до | Включён, три попытки | Выключен, после |
|---|---:|---:|---:|
| YouTube, превью YouTube, Discord, Tor, LinuxServer, Rutracker — каждый сервис | 0/1 | 3/3 | 0/1 |
| Cloudflare и TMDB API | 1/1 | 3/3 | 1/1 |
| Instagram и постер TMDB на первых выбранных адресах этого DNS | 0/1 | 0/3 | 0/1 |

Для TMDB API ожидаемым ответом является 401 без API-ключа. У LinuxServer
в выключенных фазах приходили HTTP 200 и часть страницы, но загрузка
обрывалась: это посчитано неуспехом. С включённой обработкой получены полные
страницы, проверены сертификаты; у Rutracker — по 96 400 байт, у YouTube —
примерно 0,86–0,96 МБ. Рост очереди подтверждает обработку на 87U.

Отдельное сравнение адресов оставило тот же профиль NFQWS2 и один DoT.
Другой адрес TMDB из ответа того же Quad9 и явная привязка постера дали
по три полных JPEG из трёх. Для Instagram один адрес давал таймауты,
другой — три корректных HTTPS-ответа 302. Пустое тело редиректа не является
сетевой ошибкой; это ещё не проверка входа, ленты или видео Instagram.
Через обычный DNS клиента с двумя явными адресными привязками результат
повторился. Рабочая стратегия должна описывать эти условия, а статические
IP требуют периодической проверки: CDN меняются.

Отдельная нативная проверка Instagram с переходом по редиректу дала
полную страницу входа HTTP 200, 373 745 байт, с проверенным сертификатом.
До включения NFQWS2 и после его остановки тот же запрос получал сброс.
Это подтверждает HTTPS-загрузку страницы на выбранном адресе; лента,
авторизация и воспроизведение в приложении отдельно не проверялись.

Есть и отдельный фактор — обработка на двух роутерах подряд. При неизменном
процессе 87U включение NFQWS2 вышестоящего роутера сопровождалось таймаутом
Discord, выключение — двумя полными ответами, повторное включение — снова
таймаутом. Для постера возвратная фаза не повторила отказ, поэтому такой же
строгий вывод о нём не сделан. Перед оценкой стратегии нужно знать весь путь.

Это нативная проверка маршрутизации и обработки пакетов на конкретном 87U,
дополненная виртуальным LAN-клиентом. Она не измеряет физический Wi-Fi,
скорость порта, воспроизведение видео, голос, UDP/QUIC, IPv6 или суточную
устойчивость. После опытов прежние конфиги и состояние вышестоящей службы
возвращены; рабочее соединение ПК сохранялось.

### Сравнение оригинальных проверок DPI

На 87U также выполнены группы 2/3 DPI Detector 5.0.0-alpha.21 без изменения
алгоритмов исходного проекта. Официальный ARMv7-бинарник на этой системе
завершается SIGILL; здесь использована отдельная испытательная soft-float
сборка для ARMv5TE. Она пока не входит в обычный установщик DPI проекта.

Условия: один проверяемый DoT, две явные адресные привязки, выключенный
NFQWS2 upstream. Временное собственное правило только 87U блокировало
внешние UDP/TCP запросы на порт 53: встроенные запасные DNS инструмента не могли
подменить проверяемый путь. За три фазы отклонено 255 таких UDP-запросов.

| Результат DPI | NFQWS2 выключен, до | Включён | Выключен, после |
|---|---:|---:|---:|
| TLS 1.2, успешные из 35 | 8 | 33 | 8 |
| TLS 1.3, успешные из 35 | 8 | 33 | 8 |
| TCP 16, успешные из 110 | 21 | 84 | 19 |
| QUIC ServerHello из 35 | 3 | 18 | 3 |

В фазе с обработкой две TLS-цели остались с ошибками. У QUIC 14 целей
инструмент отметил отсутствие поддержки, ещё 3 — ответ без завершения
проверяемого рукопожатия. ServerHello не подтверждает передачу видео или
произвольных UDP-данных. Полные исходные результаты сохранены, включая
неуспехи. Эти числа описывают текущую сеть, набор целей и стратегию;
они не являются обещанием результата у другого оператора.

### Память и накопитель

Испытанный RT-AC87U имеет **256 МиБ ОЗУ**, из которых Linux видит около
250 МиБ. Это объём проверенного устройства, а не доказанный минимум пакета.
Потребление NFQWS2 зависит от стратегии, Lua, списков, очередей и соединений;
DNS-кеш и параллельные запросы также требуют памяти. Для моделей с меньшей
RAM нужен отдельный замер под нагрузкой, а не обещание по одному запуску.

Самостоятельный ARMv7 IPK занимает около **2 МиБ** при загрузке и около
**6 МиБ файлов** после распаковки, без Entware, PHP и прочих зависимостей.
Обновлению дополнительно нужны копия пакета, резервная копия настроек,
временный runtime и свободный запас: проверка учитывает их размеры и резерв
16 МиБ. Это запас места в соответствующем файловом разделе, не требование
«16 МиБ RAM». На `/tmp` раздел расходует RAM, на USB — место накопителя.

Перед установкой смотрите не только `MemFree`, но и `CommitLimit`/
`Committed_AS`: старое ядро может отказать в fork/распаковке при ограничении
выделения памяти. Проверяйте одновременно:

```sh
cat /proc/meminfo
df -k /tmp /jffs /opt
```

Для старого семейства рекомендуемый путь — внешняя USB Entware с достаточным
свободным местом. Не форматируйте накопитель с данными ради установки.

Измеренные процессы в коротком контрольном опыте на 87U:

| Компонент | Наблюдение | Что это означает |
|---|---|---|
| NFQWS2 | RSS после пяти HTTPS около 0,97 МиБ; VmHWM — 1,02 МиБ | Короткий профиль с двумя Lua, один IPv4 TCP-адрес; большие списки и нагрузка не измерены |
| SmartDNS | Worker — 5,27 МиБ RSS и monitor — 0,34 МиБ RSS, вместе около 5,61 МиБ | Проверенный профиль DoT/DoH с кешем; расход зависит от кеша и запросов |
| Система в этом опыте | Linux видит 249,7 МиБ RAM; MemFree около 157 МиБ | Состояние конкретного роутера, не гарантированный свободный объём у владельца |

В более широком LAN-опыте с пользовательским профилем NFQWS2 занимал
около 1,31–1,34 МиБ RSS, наблюдаемый VmHWM — до 1,41 МиБ. В опыте с одним
DoT без кеша сумма RSS worker и monitor SmartDNS была около 3,96–4,73 МиБ;
это сумма RSS процессов, а не уникальная физическая память. Во время нативного DPI-теста наблюдаемый RSS NFQWS2 вырос до 1,79 МиБ,
VmHWM — до 1,91 МиБ; сам детектор занимал около 3,20 МиБ RSS с VmHWM
3,73 МиБ. WebUI и множество одновременных клиентов в эти замеры не входят. Эти числа помогают оценить
порядок расхода, но не устанавливают минимальные требования.

RSS процесса не включает всю память ядра, очередей и файлового кеша.
В 20-секундном DNS-тесте получены 120 успешных ответов из 120, максимум четыре
параллельных запроса, преимущественно с кешем. Это не измерение предельной
производительности, WebUI/PHP под нагрузкой или суточной стабильности.

После установки испытательного набора Entware, SmartDNS и NFQWS2 во внутреннем
JFFS оставалось около **37 МиБ** из 64 МиБ. Это не размер одного SmartDNS:
в набор входят зависимости, WebUI и дополнительные файлы. Состояние JFFS
у других владельцев отличается. Логи и временные данные следует ограничивать
и хранить в RAM; частую запись DNS-журнала во внутреннюю флеш-память включать
не нужно.

Установка всего Entware во временный `/tmp` оказалась плохой базой для этого
опыта: при распаковке пакетов старое ядро достигало лимита выделения памяти
и не могло создавать процессы, хотя свободная физическая память ещё была.
После переноса на постоянный накопитель те же пакеты установили реальные файлы.
Сообщение opkg об установке без проверки файлов и запуска недостаточно.

USB-путь также прошёл 20-секундный тест: 120 ответов из 120 при тех же шести
известных именах и максимуме четырёх параллельных запросов. Начальное RSS
после загрузки — около 4,9 МиБ. Разницу производительности USB и JFFS этот
короткий тест не измеряет. Внутренний JFFS оставлен резервом лаборатории;
пользовательская инструкция ориентируется на внешний USB.

Сразу после одной из загрузок два из 15 upstream дали SERVFAIL; оба затем
ответили во всех трёх повторах. В общем профиле все семь проверяемых имён,
включая локальное, ответили. Первоначальные ошибки сохранены, их точная
причина не установлена. Нельзя обещать мгновенную готовность каждого upstream.

С самого 87U через USB-профиль получены HTTPS-ответы 200 от YouTube,
Instagram, Discord и Cloudflare, а TMDB API вернул ожидаемый 401 без API-ключа.
Один запрос постера TMDB завершился таймаутом. Эти пробы не подтверждают
воспроизведение видео, авторизованные функции, голос или независимый обход:
влияние обработки вышестоящего роутера здесь отдельно не исключалось.

## Связка с dnsmasq

### Чей DNS и чей трафик проверяются

DNS роутера, DNS телефона и собственный DoH браузера могут идти разными
путями. Тест DPI, запущенный на роутере, проверяет трафик самого роутера.
Для исходящего запроса это обычно адрес его WAN, а не LAN. Добавление LAN-IP
роутера в список клиентов само по себе не включает обработку его запросов.
Телефон за LAN имеет другой исходный адрес; проверяйте его фактический IP
и режим включения/исключения устройств.

При сравнении записывайте модель и прошивку, источник трафика, IPv4/IPv6,
стратегию, DNS-путь и VPN либо второй обработчик выше по сети. Меняйте один
фактор за раз. Перед остановкой или перезагрузкой при отказе сохраните
диагностику; после неё часть признаков уже исчезнет.

### Передача запросов от dnsmasq

Проверяемая схема сохраняет штатный DNS-сервис ASUS:

```text
Устройства LAN → dnsmasq ASUS :53 → SmartDNS 127.0.0.1:6053 → выбранные DNS
Сам роутер     → dnsmasq ASUS :53 ─┘
```

SmartDNS слушает локальный непривилегированный порт. Его установочный скрипт
не должен самостоятельно перехватывать весь DNS или занимать порт dnsmasq.
В испытании использован `SMARTDNS_WORKMODE="0"` в
`/opt/etc/smartdns/smartdns-opt.conf` upstream-пакета.

dnsmasq продолжает обслуживать DHCP, локальные имена и свои доменные правила.
Для глобального forwarding нужны `no-resolv` и `server=127.0.0.1#6053`;
прежние глобальные upstream не должны оставаться параллельным обходным путём.
При этом нельзя без разбора удалить локальные или доменные настройки ASUS.
Форма штатной панели на испытанной прошивке не приняла DNS с произвольным
портом: одной записи `127.0.0.1:6053` в обычное поле DNS недостаточно.

Merlin заново создаёт конфигурацию dnsmasq при применении настроек. Для
постоянного варианта требуется поддерживаемый `dnsmasq.postconf`, а для Entware
на JFFS — раннее монтирование до запуска DNS. Существующие пользовательские
hooks нужно дополнять с резервной копией, а не заменять. Подробнее:
[Merlin User scripts](https://github.com/RMerl/asuswrt-merlin.ng/wiki/User-scripts),
[Custom config files](https://github.com/RMerl/asuswrt-merlin.ng/wiki/Custom-config-files).

Отдельно проверяется resolver самого роутера. На этой версии Merlin штатный
`dns_local_cache=1` после запуска dnsmasq переключает `/etc/resolv.conf`
на `/rom/etc/resolv.conf` с localhost. При этом `/tmp/resolv.conf` может
по-прежнему содержать DNS провайдера: он не обязательно используется
программами. Проверять нужно ссылку и содержимое именно `/etc/resolv.conf`,
а затем фактический DNS-запрос. Перезаписывать промежуточный файл отдельным
фоновым скриптом для этой схемы не требуется.

### DoT/DoH и явные адреса

У TLS-резолвера есть разные параметры: адрес подключения, имя для проверки
сертификата и, для DoH, HTTPS URL. Если требуется закрепить соединение за IP,
нужно сохранять правильное TLS-имя и проверку сертификата. Подмена URL на IP
и отключение проверки сертификата — не равноценная настройка.

Bootstrap-адреса позволяют начать работу, когда DNS ещё не готов. Время также
должно быть правильным: иначе проверка сертификата может отказать. Источник
времени не должен зависеть только от ещё не работающего TLS-DNS.

Правило «этот домен спрашивать у этого DNS» отличается от статического ответа
«этот домен всегда имеет этот IP». Второй вариант перестаёт следовать изменениям
CDN; такие адреса нужно проверять и иметь возможность убрать. Переносить весь
чужой DNS-профиль без понимания правил не следует.

## Ограничения установки

Старый feed Entware armv7sf-k2.6 содержит SmartDNS 43, а испытан отдельный
официальный optware runtime 48.4. Это разные способы поставки. Обычная команда
`opkg install smartdns` сама по себе не обещает установить испытанную версию.

В официальном optware IPK 48.4 старый opkg на этом аппарате падал при обработке
пустых полей `Suggests` и `Conflicts`. Контрольный пакет с удалением только этих
пустых полей устанавливался; содержимое `data.tar.gz` не менялось. Аналогичный
случай описан в [upstream issue #987](https://github.com/pymumu/smartdns/issues/987).
Исправленный лабораторный пакет пока не является опубликованным установщиком
проекта. Кнопка установки SmartDNS в нашей панели ещё не реализована.

Проверка пакетов выполнялась с локально доставленными и сверенными зависимостями.
Полный путь обычного пользователя от онлайн `opkg update` ещё требует отдельной
проверки. Успех SmartDNS не означает, что NFQWS2 поддерживается этим ядром.

В исходной проверке Build 20 без дополнительного backend postinst NFQWS2
завершался ошибкой запуска core, поэтому пакет остался в состоянии `unpacked`.
Другие операции opkg
могут снова пытаться завершить его настройку. В лаборатории использован
существующий диагностический режим:

```sh
NFQWS_ASUS_NO_START=1 /opt/bin/opkg configure nfqws2-asus
```

Он завершил конфигурацию пакета с кодом 0, сохранив core остановленным.
Это даёт установленную панель и диагностику, но не добавляет ядру обработчик
очереди. Автоматический пользовательский путь для такого случая ещё нужно
доработать; ошибку рабочего обновления нельзя скрывать тем же способом.

В Build 22 точный профиль RT-AC87U/384.13_10 уже получил проверенный backend
и исправления запуска. Это не отменяет диагностический режим на других
неподдержанных ядрах. Состояние процесса и успешный запуск не заменяют
проверку доставки пакетов и полных ответов выбранной стратегии.

### Остановка, потеря USB и авария процесса

Контролируемая проверка подтвердила: после возврата штатного forwarding
DNS отвечал без смонтированного USB и без SmartDNS. После монтирования
своей копии и выполнения post-mount связка восстановилась. Это проверка
логического отключения, а не разрешение выдёргивать работающую файловую систему.

Если остановить только SmartDNS, сохранив forwarding на 6053, dnsmasq может
возвращать REFUSED. Отсутствие живого upstream нельзя определять по кешированному
ответу: в опыте использованы новые имена. После перезапуска dnsmasq также
недостаточно увидеть новый конфиг — процесс ещё может не принимать соединения.
Готовность подтверждается ответом DNS.

Встроенный `SMARTDNS_CRASH_RESTART="1"` (`-R`) проверен при контролируемом
SIGABRT рабочего процесса. С выводом в постоянный файл RAM, как в проверенном
hook автозапуска, новый worker восстановил DNS примерно за 1,9 секунды.
Обычная остановка завершила и worker, и monitor. Сам файл вывода тоже нужно
ограничивать и ротировать.

С `-R` команда запуска может завершиться раньше появления рабочего процесса
и DNS-сокетов. В загрузочном опыте это оставило dnsmasq на прежнем upstream,
хотя SmartDNS уже был запущен. Перед перенаправлением добавлено ограниченное
ожидание PID и обоих сокетов; следующая полная загрузка подтвердила forwarding
и ответы нового, некешированного имени через штатный DNS роутера.

При запуске monitor с выводом в завершающийся SSH-канал восстановление
не наблюдалось. Поэтому прямой ручной запуск нельзя считать проверкой
boot-схемы. `-R` также не является универсальным watchdog: код upstream
не предусматривает перезапуск после SIGKILL. Потеря накопителя и недоступность
самих DNS-серверов требуют отдельной обработки, одной опции `-R` недостаточно.
[Исходник SmartDNS Release48.4](https://github.com/pymumu/smartdns/blob/Release48.4/src/smartdns.c).

## Возврат к прежнему DNS

Перед изменениями сохраняются конфигурация DNS, пользовательские hooks,
связанные настройки и фактический resolver. Для отключения схемы порядок такой:

1. Отключить только наше перенаправление и его восстановление в hooks.
2. Перезапустить штатный dnsmasq, чтобы он получил обычные upstream ASUS.
3. Проверить ответы внешних и локальных имён, а также resolver самого роутера.
4. После восстановления DNS остановить SmartDNS.
5. Удалять пакет и его файлы только после проверки, что ни один DNS-путь
   на него больше не ссылается. Entware и чужие hooks целиком не удаляются.

Если сначала остановить единственный upstream SmartDNS, а перенаправление
оставить, DNS перестанет отвечать. Резервный профиль должен описывать прежние
рабочие настройки; случайный публичный DNS не заменяет такой профиль.

### Короткая памятка по обнаруженным сбоям

| Симптом | Что выяснено и как действовать |
|---|---|
| opkg сообщает об установке, но файлов или процесса нет | На временной Entware в RAM старое ядро упиралось в лимит выделения памяти. Проверяйте код операции, файлы и реальный запуск; используйте постоянный накопитель |
| Старый opkg падает на SmartDNS 48.4 optware | В опыте причина связана с пустыми полями метаданных пакета. Лабораторное исправление не меняло runtime. Обычная установка этой версии ещё не оформлена как готовый путь проекта |
| DPI завершается с SIGILL на старом ARM | Имя ARMv7 не гарантирует нужные инструкции процессора/ядра. На 87U потребовалась soft-float сборка; не считайте такой выход сетевой блокировкой |
| Core работает, но сайт открывается лишь частично | Проверяйте полное тело ответа и повторы. В опыте одного multidisorder хватало для TLS, но не для большой страницы |
| Сам роутер или DPI обращается к другому DNS | Проверяйте фактический `/etc/resolv.conf` и запрос, а также запасные резолверы инструмента. Содержимое `/tmp/resolv.conf` само по себе не доказывает обход SmartDNS |
| Две одинаковые стратегии подряд дают иной результат | На стенде второй NFQWS2 влиял на Discord. Исключите двойную обработку на отдельном контролируемом пути, сохраняя необходимую для связи рабочую сеть |
| Сразу после загрузки отдельный TLS-DNS ещё не отвечает | В опыте некоторые upstream восстановились при повторе. Проверьте время, готовность USB/процесса/сокетов и свежий DNS-запрос; это не обещание мгновенного восстановления |
| Служебная команда вернула 75 при параллельной операции | Это код занятой блокировки управления; повтор после завершения другой операции прошёл. Не удаляйте lock-файлы и не запускайте операции обновления/остановки параллельно вручную |
| Общие счётчики mangle обнулились после проверки запуска | На испытанном современном ASUS это повторилось даже при создании пустой цепочки штатным iptables. Preflight проверяет netfilter активно. Системные счётчики таблицы и sequence очереди NFQUEUE — разные показатели; не смешивайте интервалы до и после такой проверки |

Запуск, перезапуск после аварии, возврат DNS и автозапуск после перезагрузки —
отдельные проверки. В свежей загрузке 87U подтверждён возврат USB/SmartDNS и
ручной запуск установленного S51 с автоматической загрузкой точного модуля.
Автозапуск самого NFQWS2 при boot этим опытом не принят. Также остаются
отдельными задачами физические LAN/Wi-Fi, скорость, видео, голос, IPv6 и
продолжительная работа под нагрузкой.

Подробности самого инструмента: [SmartDNS](https://github.com/pymumu/smartdns)
и [официальная документация](https://pymumu.github.io/smartdns/en/config/basic-config/).
